# План виконання лабораторної роботи 2 — OrderFlow 1.1

## Середовище

- У теці `D:\lab2` розміщено вихідний код OrderFlow 1.1.
- Перевірені інструменти: .NET SDK `10.0.401`, Git, Node.js `v22.20.0`.
- Playwright MCP додано до глобальної конфігурації Codex як `playwright` через `npx -y @playwright/mcp@latest`. Перезапустити Codex, щоб завантажити нову MCP-конфігурацію; браузер Playwright встановлюється під час першого запуску.
- Варіант потрібно взяти зі своєї ЛР1. У зразку DOCX вказано варіант 2, однак це лише приклад, не підтвердження вашого варіанта.
- Каталог ще не є Git-репозиторієм; GitHub remote не налаштований.

## 0. Підготовка

1. Визначити свій варіант за звітом ЛР1.
2. Створити GitHub-репозиторій `orderflow-lab2`, додати викладача як collaborator (для приватного репозиторію) та ввімкнути Issues.
3. Ініціалізувати локальний Git, зафіксувати отриманий вихідний код комітом `OrderFlow 1.1 as received`, підключити remote і надіслати гілку `main`. Занотувати URL та SHA.
4. Виконати `dotnet test` у корені рішення; записати останній рядок успішного виводу.
5. Запустити застосунок з `ORDERFLOW_VARIANT=<ваш номер>`, увійти як `manager`, дослівно зберегти повідомлення зі сторінки Support.

## 1. Розслідування Support (ліміт 60 хв)

- Вести часові нотатки за `kit/templates/investigation_note.md`; чітко розділяти спостереження й інтерпретації.
- Перевірити збірку/варіант, роль, стан даних, сторінку чи API. За потреби скинути демодані.
- Змінювати по одному: ввід (замовлення, товари, кількості), стан (свіжі/попередні дані), час між діями.
- Використати Outbox, Log, вкладку Network, Swagger/API або `curl -i`; зібрати статус, заголовки, тривалість, error id.
- Playwright MCP застосовувати для дій у браузері й знімків доказів. Записати кроки, роль, стан і час. Спрощувати сценарій, доки проблема не зникне, потім додавати умови, доки не з’явиться.
- Висновок має назвати одну з п’яти можливостей (спостереження, інша система, інший стан, інший ввід, неправильна модель), пояснити виключення, вирішальне спостереження та кроки відтворення або межі невдалого відтворення. Непідтверджене формулювати обережно.

## 2. Issue та значущість

- За `kit/templates/bug_report.md` створити чотири звіти: знахідка Support і три найбільш значущі підтверджені знахідки з таблиці оракулів ЛР1. Перевірити кожну на версії 1.1; питання та курйози не подавати як дефекти.
- Для кожного: назва одним реченням (приблизно 12 слів), версія/варіант/браузер/запуск, короткий опис, необхідні кроки (останній починається «Зверніть увагу, що...»), названий оракул, вплив, обхідний шлях, докази.
- Зберегти URL і повний текст кожного issue для додатка. Не редагувати issue після подання; уточнення — коментарем.
- Заповнити `kit/templates/significance_table.md`: частота, шкода, вплив на ризики, розголос, серйозність і пріоритет із коротким обґрунтуванням. Окремо пояснити вибір чорного прапора або чому жоден дефект його не заслуговує.

## 3. Історія тестування

- Описати три сесії ЛР1 та розслідування ЛР2.
- Підготувати телескопічний PROOF за `kit/templates/proof_report.md`: підсумок на два речення, абзац, розділи Past, Results, Obstacles, Outlook, Feelings.
- Заповнити `kit/templates/dashboard.md`: 5–8 областей зі схеми ЛР1, зусилля, покриття 0–3, колір якості й коментар, обґрунтований аркушами сесій та звітами.
- Оновити схему покриття рівнями Голланда (нічого; базова; більше ніж базова; типові; деякі межові; глибокі межові випадки), сховавши нижчі рівні.
- У PROOF/історії не зазначати кількості тест-кейсів або дефектів.

## 4. GitHub Actions

1. Заповнити `.github/workflows/ci.yml` для `push` і `pull_request`: `dotnet restore`, `dotnet build`, `dotnet test` для `OrderFlow.slnx`. Push; зберегти перший зелений запуск.
2. У `src/OrderFlow.Domain/Pricing.cs` змінити звичайну знижку з `0.10` на `0.25`; окремий коміт `experiment: discount rate`, push, зберегти запуск.
3. У `src/OrderFlow.Api/ApiEndpoints.cs` перейменувати `/products` на `/catalog`; окремий коміт `experiment: route rename`, push, зберегти запуск.
4. Відкотити обидва експерименти через окремі `git revert`, push і перевірити фінальний зелений запуск. Не залишати експериментальні зміни.
5. Зберегти чотири URL запусків у порядку: початковий зелений, після знижки, після маршруту, після відкату (очікувано: зелений, зелений, червоний, зелений); зняти журнал невдалого кроку.
6. Написати рефлексію приблизно на пів сторінки: що показують/не показують рівні історії тестування, що доводить зелений запуск після знижки, рівень Голланда для п’яти smoke-тестів і що ще потрібно розслідувачу.

## 5. Підсумковий звіт

Створити один `Lab2_<Прізвище>_<Варіант>.pdf` або `.docx` у такому порядку:

1. Варіант, URL репозиторію, SHA початкового коміту та чотирьох комітів експериментів/відкатів.
2. Нотатка розслідування.
3. Посилання на чотири issue.
4. Таблиця значущості й абзац про чорний прапор.
5. PROOF, панель і розфарбована схема покриття.
6. Чотири посилання на запуски CI, скриншот невдалого кроку, рефлексія.
7. Висновок на 5–10 рядків: який звіт виправлять першим і чому, що захищає конвеєр.
8. Додаток із повним текстом чотирьох issue.

## Оформлення скриншотів за DOCX-зразком

- У зразку скриншоти UI, рахунків і Swagger/API йдуть послідовно, переважно на ширину текстової області; кожен має підпис «Рис. N. …».
- Обрізати до потрібної сторінки/відповіді, залишати текст читабельним і прибирати зайві панелі браузера. Для API показувати метод/URL та відповідь, для UI — стан до/після дії.
- Розташовувати рисунок після абзацу з описом доказу й посилатися на нього в тексті. Скриншот доповнює кроки й оракул, а не замінює їх.
- Не змішувати локальне `localhost:5000` із віддаленим стендом; зазначати дату/час і роль. Не переносити результати з прикладу як власні.

## Завершальна перевірка

- Чотири issue підтверджені на 1.1, містять оракул та докази; нотатки й висновки узгоджені.
- PROOF, панель і схема спираються на фактичні сесії; у PROOF немає кількостей тестів/дефектів.
- Є чотири коміти експериментів/відкатів, чотири посилання на запуски, невдалий лог і фінальний зелений CI.
- Експерименти відкотили; повні тексти issue в додатку; рисунки підписані та читаються.
